# ark-review

> **通用性原則**：本 plugin 是通用工具，會發佈給其他使用者。個人化內容
> （帳戶設定、排程參數、專案協定、一次性調整）放執行資料夾 `~/.ark-toolkit/`
> 或專案自己的 `docs/`，**不要直接改 plugin**；只有通用的修復與功能
> （附測試）才動 plugin 本身。

決策軌的**學習迴路**：ark-agent 每天做決策並記錄理由，這裡回頭問「當初為什麼
這樣想、結果如何、下次該改什麼」，把結論寫成準則餵回決策層。

**與 ark-agent 的 evaluate 分工**：`evaluate.py` 回答「成績如何」（聚合統計，
服務實驗協定）；本 skill 回答「該改什麼」（逐筆案例與準則損益歸因）。

## 為什麼需要這條迴路

決策層每天從零開始——packet 裡沒有任何歷史，前一天犯的推理錯誤不會自己消失。
實例：2026-08-12 與 08-13 連續兩天出現同一個誤解（把「主軌檔數上限 1」讀成
「只能加碼手上那檔」，因而略過了換股這個合法選項），因為沒有任何機制把
昨天的教訓帶到今天。

## 準則的生命週期

準則存在 `packet.rules` 指向的檔案（預設 `~/.ark-toolkit/decision-rules.md`，
`ARK_RULES` 可指到專案內以便版控），每條有編號與狀態：

| 狀態 | 意義 | 決策層怎麼對待 |
|---|---|---|
| 試行 | 只有推理支持，尚無損益證據 | 可不採用，但要說理由 |
| 生效 | 已被損益證據支持 | 偏離要有强理由 |
| 淘汰 | 被自己的損益推翻 | 移到「已淘汰」段，不再注入判斷 |

**歸因鏈**：決策層採用準則時在 `rules_applied` 填編號 → journal 保留 →
`review.py` 依準則分組算前瞻報酬。沒有這條鏈，「依損益調整準則」就只是換一種
方式憑感覺：改了規則卻無從得知改對沒有。

## 流程

1. **組案例**：`review.py --since --until`（省略則預設最近 7 天）
   - 每個決策日一則：當時的 rationale、每筆單的 reason 與 ark_basis、
     實際成交價與滑價、T+5/20/60 前瞻報酬、紀律分項
   - **缺席日也是案例**——連續缺席代表系統有問題，那是最該檢討的事
   - 複盤看全部委託（含衛星軌），不像 evaluate 只取主軌
2. **看準則的實際損益**：輸出末尾的歸因表。`n_evaluated` 為 0 代表證據還沒到期，
   不能當成「這條準則沒用」
3. **更新準則檔**：
   - 損益證據支持的「試行」→ 改「生效」
   - 被損益推翻的 → 移到「已淘汰」並註明推翻它的案例
   - 這次複盤發現的新教訓 → 新增一條，狀態「試行」，寫清楚來源案例
4. **寫檢討記錄**到專案 `docs/decision-reviews/YYYY-MM-DD.md`，保留「為什麼」的
   完整脈絡——準則只留短句，理由留在這裡
5. **commit** 準則檔與檢討記錄，讓每次規則變更都有 git 歷史可追

## 誠實準則（重要）

- **證據不足就說證據不足**。T+5 最快要 5 個交易日、T+20 要一個月。實驗初期的
  準則多半是「試行」，不要把推理包裝成已驗證的結論
- **不要為運氣好的決策發明準則**。單筆賺錢不代表推理正確；樣本小且前瞻視窗
  互相重疊，`n_evaluated` 個位數時任何勝率都不具意義
- **準則只能收窄選擇，不能放寬硬邊界**。與 ARK 紀律衝突的一律作廢
- 準則總數維持在可讀範圍（約 10–20 條）。要新增時先問有沒有舊的該淘汰

## 指令

```bash
# 最近 7 天（預設）
uv run review.py

# 指定期間，用 T+20 做準則歸因
uv run review.py --since 2026-08-11 --until 2026-08-15 --horizon 20

# 機器可讀
uv run review.py --json

# 不連券商，只用本地日K快取
uv run review.py --offline
```
